# Задание 06: справочники и основа данных персонажа

Статус: done. Реализация проверена 2026-10-05; результаты в
[отчёте 06](../reports/2026-10-05-06-character-catalog-foundation.md).

## Запрос Лиду

Реализуй первый шаг этапа 3 из ТЗ v0.3: основу данных для создания персонажа.
В этой задаче я явно прошу реализацию кода, миграций и тестов, а не только подсказки.
Прочитай `AGENTS.md`, разделы 2.3, 6, 13 и 17 ТЗ и текущий код затронутых моделей.
Сначала проверь HEAD, git status и существующие изменения: рабочее дерево содержит
незакоммиченные результаты предыдущих задач. Не откатывай их и не переписывай
auth, кампании и членство. Обновляй `docs/TEAM_STATUS.md` по ходу работы.

### Цель

Получить проверенную на PostgreSQL схему: существующий персонаж связан с
версионированными справочниками расы, класса и предыстории; справочники можно
повторно загрузить одной командой без дубликатов. Это фундамент следующей задачи
с API создания черновика, а не реализация всего листа персонажа.

### Объём реализации

1. Добавь модели справочников рас / видов, классов и предысторий. Предусмотри
   стабильный код, название, описание, набор правил `dnd-2024`, версию контента,
   источник и лицензионную атрибуцию, доступность для нового выбора.
   Выбранный способ хранения кратко обоснуй; не строй универсальный rules engine.
2. Заложи типизированные данные для стартовых прибавок предыстории: три допустимые
   характеристики и выбор +2/+1 либо +1/+1/+1. Отдели описание от исполняемых
   эффектов. Не добавляй произвольные выражения / eval и не приписывай классам
   несуществующие фиксированные прибавки к характеристикам. Сам расчёт — позже.
3. Адаптируй существующий `Character`: имя, ссылки на версии трёх справочников,
   уровень с default 1 и ограничением > 0. Сохрани `campaign_member_id`, его
   уникальность, статусы и причину архивации. Не добавляй личную биографию,
   дублирующие owner/campaign связи или отдельную `CharacterInfo` без необходимости.
   Уникальность персонажа действует и после архивирования.
4. Добавь новую миграцию от фактического текущего Alembic head. Не редактируй
   применённые миграции и не очищай БД. Проверь расхождения текущей модели и
   миграций: текстовые race / character_class нельзя молча заменить случайными
   ссылками. Для существующих строк нужен проверяемый перенос без потери данных;
   если однозначного соответствия нет, сохрани данные переходной схемой и
   отдельно запроси сопоставление перед ужесточением NOT NULL. Не подставляй
   выдуманную предысторию. Миграции выполняй только на выделенной тестовой БД.
5. Добавь отдельную идемпотентную команду начальной загрузки и минимальный
   проверенный набор из SRD 5.2.1: хотя бы по одному варианту каждой категории.
   Сохрани требуемую атрибуцию. Повторный запуск не меняет опубликованные версии;
   изменение содержимого под существующим кодом и версией должно обнаруживаться,
   а не переписывать данные. Это технический стартовый набор, не полный каталог.
6. Добавь тесты моделей, ограничений и загрузки; документируй команду и порядок
   «миграции — загрузка» в README. Если для задачи нужны специалисты, следуй
   правилам владения файлами из AGENTS.md; цепочка миграций имеет одного автора.

### За пределами задачи

Не реализуй HTTP-ручки, броски, распределение, вычисление итогов, согласование
мастером, инвентарь, frontend, загрузку аватаров, импорт всех книг или редактор
справочников. Не меняй инфраструктуру без выявленной необходимости. Не делай
коммит и push без отдельного запроса. Не трогай пользовательскую БД.

### Критерии готовности

- Миграции разворачивают схему с нуля на отдельной PostgreSQL и корректно
  обновляют предыдущую схему с тестовыми данными, не уничтожая их.
- Внешние ключи и ограничения реально отклоняют неверные ссылки, повторного
  персонажа для того же членства, уровень <= 0 и удаление используемых версий.
- Уровень по умолчанию равен 1. Неактуальные версии сохраняются для старых листов.
- Повторная загрузка не создаёт дубликатов и не меняет закреплённое содержимое.
- Документировано, какие проверки принадлежат будущему сервису: роль Player,
  активная кампания и совместимость выбранных версий. Тест модели не объявляется
  доказательством работы ещё не реализованного API.
- Пройдены `uv sync --frozen`, `uv run ruff check .`, `uv run mypy app`,
  `uv run pytest` и относящиеся PostgreSQL-интеграционные тесты по README.
  Укажи фактические команды и результаты; mocks не заменяют реальную БД.
- Существенные изменения проверены независимо по правилам AGENTS.md; Лид
  прочитал итоговый diff, ограничения, перенос данных и совместимость.
- Есть отдельный отчёт в `docs/reports/` с номером 06: изменения, проверки,
  ограничения / блокеры и следующий шаг. TEAM_STATUS обновлён.

Если безопасный перенос существующих данных требует выбора владельца проекта,
не угадывай его. Выполни независимую часть и явно отдели готовое от блокированного.
