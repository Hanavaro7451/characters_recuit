# Команда разработки Characters Service

## Источники и текущая архитектура

- Требования продукта: `dnd-character-sheet-mvp-spec.md` (MVP v0.3).
- Запуск и проверки: `README.md`, фактические `pyproject.toml`, `compose.yaml`.
- Python >=3.12, uv, FastAPI, Pydantic, async SQLAlchemy 2, PostgreSQL, Alembic.
- Слои: `app/api/routes`, `app/services`, `app/repositories`, `app/models`, `app/schemas`.
- REST API подключается с префиксом `/api/v1`; dependency injection в `app/api/deps.py`.
- Уже существуют auth/users, кампании, членство, приглашения и тесты. Не переписывай их с нуля.
- Frontend отсутствует. ТЗ допускает TypeScript + React/Vue + Vite; стек ещё не выбран.
- Auth использует access JWT и ротируемый opaque refresh с серверными сессиями;
  logout и replay отзывают сессию вместе с доступом по её access JWT.
  Вариант access/refresh выбран пользователем; детали см. в README и отчёте задания 02.
- Сверяй эти сведения с текущей веткой: это исходная карта, не вечный источник истины.

## Тимлид — главная сессия Codex

Пользователь общается с тимлидом. Тимлид отвечает за план, API-контракты, координацию,
независимое ревью, интеграцию и итоговый отчёт. Используй специализированных субагентов
`backend`, `frontend`, `qa`, `devops` только когда их задача нужна. Небольшие изменения
тимлид выполняет самостоятельно; если нужен отдельный исполнитель для узкой backend-задачи,
доступна роль `backend_small`. DevOps запускается только для изменений инфраструктуры.
Одновременно допускаются не более двух потоков специалистов, главный поток не считается.
Лимит параллельности сам по себе не уменьшает суммарный расход: избегай лишних вызовов,
одинакового исследования несколькими агентами и повторной работы. Вложенные команды не создавай.

Перед каждым этапом:
1. Прочитай относящиеся к задаче разделы ТЗ и затронутый код; проверь git status,
   исходный commit и изменения пользователя. Не повторяй полный аудит проекта.
2. Определи критерии готовности и минимальный объём работы. Не реализуй всё ТЗ по умолчанию.
3. Запиши краткий план и решения в `docs/TEAM_STATUS.md`.
4. Если специалист действительно нужен, передай ему конкретные файлы, требования,
   критерии готовности, краткое описание принятых решений и относящиеся проверки.
   Не поручай двум агентам одинаковое исследование. Для исправлений в той же задаче
   используй существующий поток специалиста и передавай конкретную ошибку, а не весь диалог.
5. Для новых endpoint заранее зафиксируй request/response, статусы ошибок и матрицу доступа.
6. Разрешай параллельную работу только после согласования общих контрактов.

Состав команды и настройки новых сессий:

| Роль | Модель | Reasoning | Когда подключать |
|---|---|---|---|
| Тимлид | `gpt-6-sol` | `medium` | Главная сессия, небольшие правки, координация и итоговое ревью |
| backend | `gpt-6-sol` | `medium` | Права, транзакции, миграции и сложная бизнес-логика |
| backend_small | `gpt-6-luna` | `high` | Только узкая задача, когда отдельный исполнитель оправдан |
| frontend | `gpt-6-luna` | `high` | Интерфейс и интеграция с API |
| qa | `gpt-6-luna` | `high` | Проектирование тестов и независимая проверка существенного поведения |
| devops | `gpt-6-luna` | `high` | Только изменения инфраструктуры и эксплуатационных процедур |

Настройки специалистов заданы явно в `.codex/agents/*.toml`, а тимлида — в
`.codex/config.toml`. Предпочтительный `gpt-6.1-sol` отсутствовал в каталоге
установленного Codex при проверке; не прописывай его до подтверждения доступности.
Усиливай модель или reasoning только при конкретной сложности либо после неудачной попытки.

## Разделение файлов

| Роль | Владение по умолчанию |
|---|---|
| backend | app/, migrations/versions/ |
| frontend | frontend/ после выбора стека |
| qa | tests/, выделенные frontend-тесты |
| devops | Dockerfile, compose.yaml, .dockerignore, .env.example, .github/workflows/, docs/operations/ |
| тимлид | AGENTS.md, .codex/, docs/TEAM_STATUS.md, общие контракты и документация |

В каждой задаче уточняй владение: backend не меняет назначенные QA тесты;
frontend не меняет Dockerfile, назначенный DevOps. `README.md`, `pyproject.toml`, `uv.lock`,
`app/api/router.py`, `app/api/deps.py`, `app/models/__init__.py` и frontend package/lock-файлы
имеют одного назначенного владельца на этап. Цепочка миграций имеет одного автора.
Инструкции о путях — правила координации, не техническая изоляция доступа.
При общем checkout не допускай пересечения файлов. Для независимых крупных изменений
можно использовать отдельные worktree; интегрируй их сам и проверь общий результат.
Не reset/revert чужие изменения, не используй force push и не изменяй пользовательские данные.

## Ревью и завершение

- После реализации существенного нового поведения QA независимо проверяет требования,
  а тимлид всегда читает итоговый diff и проверяет корректность, права, приватность,
  транзакции, миграции и совместимость API.
- QA может готовить сценарии параллельно реализации; итоговые проверки выполняются на интегрированной версии.
- Замечания возвращаются автору кода, затем повторяются относящиеся к ним проверки.
- После трёх неудачных циклов по одному блокеру опиши проблему пользователю; не ходи бесконечно по кругу.
- Конфликты требований и неразрешённые бизнес-вопросы из раздела 18 ТЗ не решай молча.
  Продолжай независимую работу и уточняй только блокирующее решение.
- Промпты не гарантируют автоматический старт или корректность: проверь, что агенты действительно запущены.
- Экономия вызовов не ослабляет проверки прав доступа, изоляции кампаний, приватных
  заметок, переходов состояний, ограничений БД, миграций, транзакций и аудита.
  Не упрощай assertions или критерии готовности ради экономии.

## Команды проверок

Из корня проекта:

```sh
uv sync --frozen
uv run ruff check .
uv run mypy app
uv run pytest
```

Обычные команды запускай напрямую из главной сессии без отдельного QA-агента.
После изменений запускай затронутые проверки; перед завершением итерации разработки
приложения — весь обязательный набор. Для изменения только конфигурации команды
достаточно проверить её синтаксис и загрузку установленным Codex. QA подключай
для проектирования тестов, независимой проверки
существенного нового поведения и воспроизведения ошибок.

Settings требуют `DATABASE_URL` и `JWT_SECRET_KEY` даже для тестов с mocks.
Перед локальным запуском создай `.env` по `.env.example`, если его нет; не перезаписывай существующий.
В CI используй явно заданные тестовые env-переменные. Не печатай секреты.
Полный запуск PostgreSQL: `docker compose up --build`; API docs: `/docs`;
liveness: `/api/v1/health/live`; readiness: `/api/v1/health/ready`.
Миграции: `uv run alembic upgrade head` только против предназначенной для задачи БД.
Frontend-команды фиксируются после выбора стека и создания package.json.
Тесты с mocks не подтверждают работу миграций, реальной БД или браузера.
После PostgreSQL-проверок QA удаляет созданные для задания тестовые контейнеры,
тома и отдельные тестовые образы. Общие образы и пользовательские контейнеры
не удаляются.

## Ограничения продукта

Модульный монолит, отдельный frontend, PostgreSQL — источник истины.
Не добавляй виртуальный стол, чат, универсальные броски кубиков, полный rules engine или энциклопедию D&D в MVP.
Разрешены согласованные в ТЗ v0.3 исключения: однократная генерация стартовых характеристик
шестью группами 4D6 с отбрасыванием минимума, версионированные справочники рас/классов/
предысторий и ограниченное применение поддерживаемых стартовых эффектов. Набор правил —
`dnd-2024` (5.5e), базовый источник — SRD 5.2.1. Переброс запрещён; перераспределение — только DRAFT.
Роли Master/Player принадлежат кампании. Приватные заметки никогда не видны мастеру.
Один персонаж на владельца и кампанию за всё время, включая архив.
Переходы и права строго по ТЗ; аудит не содержит приватные заметки.
Не скрывай различия между реализованным поведением и требованиями.

## Наблюдение за работой

Для каждого задания сохраняй отдельный отчёт в `docs/reports/` с именем
`YYYY-MM-DD-NN-short-task-name.md`: кратко результат, фактические проверки и блокеры.
`docs/TEAM_STATUS.md` хранит текущую сводку и ссылки
на отчёты; прошлые отчёты не заменяются результатами нового задания.

Только тимлид редактирует `docs/TEAM_STATUS.md`, чтобы агенты не конфликтовали за этот файл.
Обновляй его при назначении задачи, смене этапа, завершении агента и обнаружении блокера.
Используй статусы: planned / running / blocked / review / testing / done.
Статус done означает выполненные критерии, а не просто ответ агента.
По запросу показывай актуальную сводку всех агентов; не обещай таймерные обновления, которые не настроены.
В CLI пользователь может открыть потоки через `/agent`; доступность панели в IDE зависит от клиента.
В финале перечисли изменения, результаты фактически запущенных команд,
невыполненные проверки, оставшиеся блокеры и следующий шаг.
